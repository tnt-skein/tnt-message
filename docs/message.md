# Общая часть договора очереди

`tnt-message` — то, что у очередей сообщений общее и потому исполняется
одним кодом: конверт, проверка настроек отправки и тела, приговор
обработчику, область, в которой обработчик идёт, крюки отправки
и обработки и ряды метрик. Очередь пишет своё — взятие и итог у рока или брокера,
свои признаки и свои тексты отказов, — а общее берёт отсюда.

```lua
local message = require('tnt.message')

local given = message.options({ key = 'order-7' }, { key = true }, 1)
local envelope = message.envelope('orders', { order = 7 }, given)

assert(#envelope.id == 26 and envelope.key == 'order-7' and envelope.attempt == 0)
```

## Зачем пакет

Очередь в спейсах, шина внутри узла, ящик исходящих и клиенты брокеров
обещают обработчику одно и то же: тот же конверт, те же настройки
отправки, тот же итог. Ради этого очереди и держат общий договор —
обработчик, написанный для одной, переезжает на другую без правки.

Обещание держится, только пока его исполняет один код. Копии, написанные
каждой очередью своими словами, расходятся молча: одно и то же тело одна
очередь принимает, а другая отвергает, и расхождения не видит ни одна
проверка — каждая копия проверена у себя и права по-своему. Проверка
дублей копий не видит тоже: слова в них разные. Поэтому общее живёт
в одном пакете и проверяется однажды.

Отказов парой у пакета нет: всё, что он отвергает, — ошибка программиста
(незнакомая настройка, настройка, которой очередь не умеет, тело не из
простых данных) и бросается на строке того, кто позвал очередь. Своего
типа отказа нет тоже: приговор читает отказ обработчика по полям
`retriable` и `retry_after`, чей бы этот отказ ни был.

Зависимости — `tnt-must` (проверки аргументов), `tnt-context` (заголовки
и область контекста), `tnt-id` (ULID), `tnt-clock` (время отправки),
`tnt-log` (записи о броске обработчика и сорвавшемся крюке), `tnt-metrics`
(ряды в реестре встроенного `metrics`) и `tnt-external` (подмена часов
ожидания в проверках).

## Как пользоваться

Пакет — набор функций без состояния, кроме списков крюков. Уровень вины
(`level`) у проверок тот же, что второй аргумент `error`: очередь,
которая зовёт проверку прямо из своего `send`, передаёт `2`, и отказ
показывает на строку её вызывающего.

### Конверт

```lua
local context = require('tnt.context')

local sent = context.run({ request_id = 'r-7' }, function()
    return message.envelope('mail', { to = 'a@example.org' }, { headers = { tenant = 'shop' } })
end)

assert(sent.headers['x-request-id'] == 'r-7' and sent.headers.tenant == 'shop')
assert(sent.name == 'mail' and sent.attempt == 0 and sent.created > 0)
```

`envelope(name, body, opts)` собирает конверт
`{ id, name, body, headers, key, attempt, created }` в миг отправки:

- **`id` ставит отправитель** — ULID, если в настройках нет готового
  `id`. Номер задачи в спейсе после опустошения начинается заново,
  номер доставки у брокера принадлежит каналу, смещение повторной записи
  другое — по ним повтор не отсечь. ULID несёт время в старших битах;
- **`headers` — контекст этого мига**, `context.export()`, и поверх —
  заголовки вызывающего: они главнее. Так опознаватель запроса и трасса
  доезжают до обработчика на другом узле;
- `attempt` — ноль до первой выдачи; счёт выдач ведёт очередь.

`headers(own)` — то же без конверта: для того, кто кладёт заголовки
в свою строку и отправляет позже.

### Настройки отправки и признаки

```lua
local FEATURES = { key = false, delay = false, ttl = true, priority = true }
local SENDING = { unable = { key = 'порядка по ключу брокер не обещает' } }

local ok, err = pcall(message.options, { key = 'a' }, FEATURES, 1, SENDING)

assert(not ok and err:find('настройки отправки: «key» — порядка по ключу брокер не обещает', 1, true))
assert(message.options({ ttl = 60 }, FEATURES, 1).ttl == 60)
```

`options(opts, features, level, how)` проверяет настройки отправки —
`headers`, `key`, `delay`, `ttl`, `priority`, `id`, `timeout` — и отдаёт
их:

- **незнакомый ключ — исключение**, а не молчаливый пропуск: опечатка
  в имени иначе молча отменяла бы настройку;
- **настройка, которой очередь не умеет, — исключение с причиной.**
  У `key`, `delay`, `ttl` и `priority` имя настройки — имя признака
  в `features`; `false` — не умеет. Признак сверяется раньше рода
  значения: о настройке, которой очередь не умеет, важнее узнать, что
  она лишняя. Из двух запретных называется всегда одна — по порядку
  `key`, `delay`, `ttl`, `priority`;
- **сроки — не больше ста лет** (`MAX_SECONDS`): `delay` от нуля, `ttl`
  больше нуля и меньше потолка, `priority` — целое не меньше нуля,
  `timeout` больше нуля; имена заголовков — строчными буквами, значения —
  строки.

`how` называет то, что у очереди своё: `what` — как зовутся настройки
в отказе (по умолчанию «настройки отправки»), `unable` — причины
по имени признака, `cannot` — причина для всех остальных (по умолчанию
«эта очередь не умеет»). Отказ звучит `<what>: «<настройка>» — <причина>`.

`features(given, names, features, level, how)` — сама сверка признаков
по списку имён, для своих настроек очереди.

### Тело

```lua
local function deep(levels)
    local root = {}
    local node = root

    for _ = 1, levels do
        node.next = {}
        node = node.next
    end
    return root
end

assert(message.explain({ order = 7, tags = { 'a', 'b' } }) == nil)
assert(message.explain({ at = print }) == 'тело.at — простые данные, а не function')
assert(message.explain({ [1.5] = 'полтора' }) == 'тело: ключ-число — целое, а не 1.5')
assert(message.explain(deep(99)) == nil)
assert(message.explain(deep(100)) == 'тело — вложенность глубже 100 таблиц')

local shared = { leaf = 1 }
for _ = 1, 20 do
    shared = { left = shared, right = shared }
end
assert(message.explain(shared) == 'тело — не больше 10000 значений')
```

`body(body, level)` бросает, `explain(body)` отдаёт текст отказа либо
`nil`. Тело годится, если это простые данные в пределах:

- **простые данные** — `nil`, логика, конечное число, строка и таблицы
  из них с ключами-строками и целыми ключами-числами. Такое тело
  одинаково ложится и в msgpack кортежа, и в JSON брокера. Дробный ключ
  msgpack пишет, а JSON бросает на нём исключение: тело легло бы
  в очередь в спейсе и упало бы у брокера — поэтому он отказ. cdata (`int64`,
  `decimal`, `uuid`, `datetime`, `box.NULL`) в JSON теряет род, функция
  не ложится никуда, NaN и бесконечность JSON пишет словами, которых
  обратно не прочесть. Большое целое едет строкой;
- **вложенность — не глубже `MAX_DEPTH` = 100 таблиц**, считая корень.
  Кодеки `msgpack` и `json` отказывают на 129-й таблице, а очередь кладёт
  тело глубже, чем его видит отправитель: в конверт, а конверт —
  в кортеж. Сотня оставляет этому запас;
- **значений — не больше `MAX_VALUES` = 10 000**: корень, каждое значение
  в каждой таблице и каждая ссылка на таблицу — по разу. Таблица,
  положенная в две ветки, считается дважды, потому что кодек и пишет её
  дважды: положенная в две ветки на каждом из двадцати уровней, она
  пишется миллионом копий. Отказ приходит на первом значении сверх
  предела;
- **кольцо** — таблица, лежащая на своём же пути, — отказ; та же
  таблица в соседних ветках кольцом не считается.

Отказ называет место: `тело.order.items.3 — конечное число, а не nan`.

### Форма тела

```lua
local ORDER = {
    from = function(value)
        if type(value) == 'table' and type(value.order) == 'number' then
            return value
        end
        return nil, { order = 'обязательное число' }
    end,
}

local ok, err = pcall(message.conform, ORDER, { order = 'семь' }, 'очереди orders', 1)

assert(not ok and err:find('тело для очереди orders не по форме: order: обязательное число', 1, true))
assert(message.listed({ b = 'два', a = 'один' }) == 'a: один; b: два')
```

Очередь может объявить форму `tnt-data` — таблицу с `from(value)`,
отдающей значение либо `nil, errors`. `conform(shape, body, where, level)`
сверяет тело при отправке: негодное — исключение, это данные самого
приложения. `listed(errors)` — отказы формы одной строкой по порядку мест.

### Настройки получателя и приговор

```lua
local policy = message.policy({ max_attempts = 3, backoff = { base = 0.5 } }, { atomic = false }, 1)

assert(policy.workers == 1 and policy.max_attempts == 3 and policy.atomic == false)
assert(message.decide(true, nil, nil, 1, policy) == 'ack')

local verdict, delay = message.decide(true, nil, { retry_after = '2', message = 'занято' }, 1, policy)
assert(verdict == 'retry' and delay == 2)

verdict, delay = message.decide(true, nil, 'занято', 2, policy)
assert(verdict == 'retry' and delay == 1)

local reason
verdict, reason = message.decide(false, 'деление на ноль', nil, 3, policy)
assert(verdict == 'bury' and reason == 'попыток 3 из 3: деление на ноль')
```

`policy(opts, features, level, how)` проверяет настройки получателя
и ставит умолчания: `workers` — 1, `max_attempts` — 5, `backoff` —
`{ base = 1, max = 60 }`, `atomic` — `false`. `atomic` у очереди, которая
его не умеет (`features.atomic == false`), — исключение с причиной
из `how.unable.atomic`: и `atomic = false` тоже, потому что настройка,
которой нет, не значит «выключено». Свои настройки очереди называются
в `how.own` описанием `must.options`; они проверяются по роду
и отдаются вторым значением как пришли — границы и умолчания у них
забота очереди.

`decide(ok, value, err, attempt, policy)` — приговор обработчику;
первые три аргумента — ровно то, что отдал `xpcall`:

| Обработчик | Приговор |
|---|---|
| вернул значение или ничего | `ack` |
| вернул `nil, err` или `false, err` | `retry` с отсрочкой; выдача номер `max_attempts` и дальше — `bury` с причиной «попыток N из M: …» |
| вернул отказ с `retriable == false` | `bury` сразу: повтор негодного тела ничего не даст |
| бросил | как отказ, причина — текст брошенного |

**Отсрочка** — `retry_after` отказа, если он читается `tonumber`
неотрицательным числом секунд, иначе отступ `base · 2^(attempt−1)`,
но не больше `max`. Клиент HTTP кладёт в `retry_after` заголовок
`Retry-After` как пришёл, строкой, и обработчик, вернувший отказ 429
как есть, повторяется тогда, когда просил сервер. Дата, отрицательное
и NaN числом секунд не читаются — повтор идёт по отступу: дата меряется
часами сервера, а они расходятся с нашими. Бесконечная просьба упирается
в потолок `MAX_SECONDS`.

`text(reason)` — текст причины: поле `message` у таблицы, иначе
`tostring`. `refusal(message, policy, shape)` — почему выданное
зарывается, не доходя до обработчика: выдача сверх `max_attempts`
(прежние выдачи итога не вернули — сообщение, роняющее процесс, иначе
ходило бы по кругу) и тело не по форме (вход из очереди недоверенный).

### Область обработчика

```lua
local log = require('tnt.log').new('tnt.jobs')
local hooks = message.hooks('tnt.jobs')
local seen

local delivered = {
    id = '01J0000000000000000000000X',
    name = 'jobs',
    body = { job = 1 },
    headers = { ['x-request-id'] = 'r-9' },
    attempt = 1,
    created = 0,
}

local verdict = message.judge(hooks, log, delivered, policy, message.invoker(function(job)
    seen = context.get('request_id')
end))

assert(verdict == 'ack' and seen == 'r-9')
```

`judge(hooks, log, message, policy, invoke)` исполняет обработчик для
выданного сообщения и выносит приговор:

- **контекст отправителя** — `context.import(message.headers)`: вход
  недоверенный, и в область попадают только объявленные ключи. Без
  `request_id` у сообщения свой ULID: запись обработчика без опознавателя
  в журнале не найти. Повторная выдача несёт те же заголовки — это одна
  история;
- **крюки `handle`** оборачивают обработчик вместе с областью: крюк трассы
  берёт родителя из заголовков конверта;
- **бросок** пишется в журнал очереди `error` с `id`, назначением,
  номером выдачи и стеком; тело в журнал не пишется — в нём бывают
  персональные данные.

`invoke(message)` отдаёт то же, что `xpcall`. `invoker(handler)` —
исполнение по умолчанию; очередь, которой нужно больше (транзакция
вокруг обработчика), пишет своё с тем же `caught` — обработчиком `xpcall`,
который отдаёт брошенное и стек отдельно.

### Крюки

```lua
local calls = {}

hooks.set('timing', function(call, proceed)
    local sent, err = proceed()

    table.insert(calls, call.kind .. ' ' .. call.name)

    return sent, err
end)

local id = hooks.around({ kind = message.SEND, name = 'jobs' }, function()
    return 'опознаватель'
end)

assert(id == 'опознаватель' and calls[1] == 'send jobs')
assert(hooks.names()[1] == 'timing')

hooks.set('timing', nil)
```

`hooks(label)` отдаёт список крюков очереди по её имени — один на процесс:
фасад очереди и её работник берут один и тот же. Крюк —
`hook(call, proceed)`, где `call = { kind = 'send' | 'handle', name,
message }`; вид обращения один у всех очередей, и крюк трассы или замера,
написанный однажды, ставится каждой.

- `set(name, hook)` ставит, заменяет или снимает (`nil`) крюк; замена
  остаётся на прежнем месте: крюк ставят и при старте, и при перечитывании
  настроек. `names()` — имена по порядку постановки.
- `around(call, proceed)` исполняет `proceed` внутри всех крюков снаружи
  внутрь и отдаёт его итог. `proceed` исполняется один раз, сколько бы
  крюк его ни звал; что вернул сам крюк, не читается.
- **Сорвавшийся крюк ничего не срывает**: бросивший и не позвавший
  `proceed` пропускаются, `proceed` зовёт пакет сам, и пишется `warn`
  «крюк сорвался и пропущен» в журнал очереди с подавлением повторов.
  Отменить отправку крюк не может: телеметрия не решает, уйдёт ли
  сообщение.
- **Бросок самого обращения — не срыв крюка.** Крюк, пропустивший бросок
  `proceed` наружу, — а так поступает и крюк трассы — записи не получает,
  бросок уходит вызывающему тем же значением, что бы ни сделал с ним
  крюк, и обращение второй раз не исполняется: иначе сообщение, чья
  отправка уже бросила, ушло бы снова.

На отправке конверт собирается **внутри** `proceed`: тогда заголовки
несут контекст, который завёл крюк, — отрезок трассы `producer`.

### Ряды метрик: `tnt.message.series`

Ряды договора одни у всех очередей: имена `message_*` и метка
`destination` — имя очереди, темы или события. Панель и правило тревоги,
собранные для одной очереди, читают любую, а обработчик, переехавший
с шины на очередь в спейсе, остаётся на тех же графиках. Объявление
одно и лежит здесь, отдельным модулем: копии объявления в каждой очереди
однажды разошлись бы описанием или метками, а реестр второе объявление
того же ряда с другими словами отвергает исключением.

```lua
local clock = require('tnt.clock')
local series = require('tnt.message.series')

local counts = { sent = 0, ack = 0, retry = 0, bury = 0, late = 0, expired = 0, failures = 0 }

series.count(counts, 'mail', 'sent')          -- счётчик status() и ряд одним вызовом
series.count(counts, 'mail', 'ack')
series.refused('mail', { kind = 'unreachable' })
series.taken('mail', { attempt = 1, created = clock.realtime() - 0.25 })

series.depth('tnt.jobs', function()
    return { mail = { ready = 3, taken = 1, delayed = 0, dead = 0 } }
end)

assert(counts.sent == 1 and counts.ack == 1)
```

Выкладка узла после этого (строки `_bucket` опущены):

```
message_sent_total{destination="mail"} 1
message_handled_total{destination="mail",outcome="ack"} 1
message_send_failures_total{destination="mail",kind="unreachable"} 1
message_wait_seconds_sum{destination="mail"} 0.25000166893005
message_wait_seconds_count{destination="mail"} 1
message_depth{destination="mail",state="ready"} 3
message_depth{destination="mail",state="taken"} 1
message_depth{destination="mail",state="delayed"} 0
message_depth{destination="mail",state="dead"} 0
```

| Ряд | Род | Метки | Что значит |
|---|---|---|---|
| `message_sent_total` | counter | `destination` | отправлено |
| `message_send_failures_total` | counter | `destination`, `kind` | отказ отправки по роду: `unreachable`, `denied`, `busy`, `timeout`, `broken`, `rejected`, `conflict`, `closed`, `overflow` |
| `message_handled_total` | counter | `destination`, `outcome` | итог обработки: `ack`, `retry`, `bury`, `late` |
| `message_expired_total` | counter | `destination` | выброшено по сроку жизни `ttl` |
| `message_worker_failures_total` | counter | `destination` | сбоев шага работника |
| `message_wait_seconds` | histogram | `destination` | сколько сообщение ждало первой выдачи, корзины от 10 мс до часа (`series.WAIT_BUCKETS`) |
| `message_depth` | gauge со сбором | `destination`, `state` | сколько лежит: `ready`, `taken`, `delayed`, `dead` |

- `count(counts, name, what)` прибавляет единицу к счётчику `status()`
  очереди `counts[what]` и к ряду этого счётчика: `sent` — к отправленным,
  `ack`, `retry`, `bury`, `late` — к итогам, `expired` — к истёкшим,
  `failures` — к сбоям работника. Счётчик и ряд растут одним вызовом,
  и разойтись им нечем. Счётчика, у которого ряда нет, `count` не знает:
  подробности очереди (сколько работник ждал записи, сколько пропало
  с остановкой) рядами договора не становятся.
- `refused(name, err)` считает отказ отправки по `err.kind`. Список родов —
  все роды договора, и род, которого у очереди не бывает, в выкладке
  просто не появляется; незнакомый род идёт словом `_other`.
- `taken(name, envelope)` меряет ожидание на первой выдаче — от отметки
  `created` конверта до этого мига. Повторная выдача ждала отсрочки
  повтора, а не очереди, и не мерится; чужое содержимое очереди
  (`foreign`) и конверт без отметки — тоже. Часы разных узлов расходятся,
  и отрицательное ожидание — ноль.
- `depth(owner, measure)` ставит источник глубины очереди под именем
  её пакета; `nil` снимает его. Источник зовётся перед каждой выкладкой
  и отдаёт `{ [имя] = { ready, taken, delayed, dead } }`.

**Глубина — одна шкала со сбором на все очереди.** Источник у шкалы
один, и очередь, объявившая её своим источником, отняла бы ряд
у соседа: глубина очереди в спейсе пропала бы из выкладки, как только
приложение взяло шину. Поэтому источник шкалы здесь, а очереди кладут
в него свои — под именем пакета, чтобы пакет, загруженный заново, заменил
свой источник, а не добавил второй. Одно имя назначения у двух очередей
складывается по состоянию, как складываются их счётчики. Назначение,
которого источник больше не назвал, из выкладки уходит само.

Потолок назначений в рядах — сто (`series.DESTINATIONS`): очереди
и события объявляет код, а не данные, и сверх сотни назначение идёт
словом `_other`. Часы ожидания — внешняя зависимость (`realtime`)
и подменяются `series._set_source`.

## Чем пришлось поступиться

- **Предел тела — и для шины в памяти.** Шине самой годилось бы любое
  значение, но обработчик шины обязан без правки переехать на очередь
  в спейсе и к брокеру, а там кодек тело глубже 128 таблиц не запишет.
- **Сотня таблиц — меньше, чем может кодек.** Запас в 28 уровней уходит
  на то, чем очередь оборачивает тело; очередь, которая оборачивает
  глубже, должна сама мерить свою обёртку.
- **Счёт ссылок, а не таблиц.** Тело, где одна таблица лежит в тысяче
  веток, отвергается, хотя в памяти оно маленькое: кодек напишет его
  тысячу раз, и в очереди оно станет большим.
- **Разреженный список и таблица из ключей обоих родов проходят.**
  Целый ключ вне ряда `1..n` — ноль, отрицательный, после дыры — JSON
  пишет строкой, а msgpack числом, и обработчик на брокере получит ключ
  другого рода, чем на очереди в спейсе; дыру в коротком списке JSON
  пишет `null`. Договор это называет, но не отвергает: такое тело хотя бы
  ложится в оба кодека, а отказ ему отнял бы у приложения обычные
  таблицы.
- **Списки крюков — состояние процесса.** Крюк, поставленный одной
  очереди, достаётся всем её экземплярам в процессе: очереди собираются
  и внутри других пакетов, и до их настроек приложение не дотягивается.
  Проверки снимают свои крюки сами.
- **Шкала глубины ставит, а не прибавляет.** Когда назначений больше ста,
  все лишние идут словом `_other`, и строка `_other` показывает глубину
  одного из них, а не сумму: сверх потолка теряется и разбивка, и число.

## Проверки

Проверки — в `test/`, на luatest, все в процессе: ни `box`, ни сети
пакету не нужно. Тело проверяется на границах пределов — 100 и 101
таблица, 10 000 и 10 001 значение, общая таблица на двенадцати
и одиннадцати уровнях, — приговор — на всех родах отказа и строках
`retry_after`, крюки — на порядке, замене, двойном `proceed`,
сорвавшемся крюке и броске самого обращения сквозь крюк, область —
на контексте, своём `request_id` и записи броска. Ряды читаются из реестра
так, как их видит сборщик: каждый счётчик и его ряд, все роды отказа
и незнакомый, ожидание только первой выдачи и с часами впереди, корзины,
глубина двух источников с общим назначением, замена и снятие источника.
Покрытие строк и убитых мутантов — 100 %.
